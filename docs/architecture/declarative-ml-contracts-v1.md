# Declarative Atlas ML contracts v1 (Story #41)

These contracts describe identity and lineage. They do not approve a target,
data source, model, release, Snowflake object, or Arize telemetry. The
repository owns the declarations and offline validator in
`src/lyme_gap_atlas_ml/contracts.py`. The matching
`declarative-ml-contracts-v1.schema.json` describes the structural JSON shape;
the Python validator enforces cross-reference, collision, and secret-key rules
that structural schema cannot express. Governed ingestion and canonical source
normalization remain in the data repository. Model-specific target and metric
decisions remain with #23 and #30.

## Identity and relationships

Use lowercase kebab-case IDs and `vN[.N[.N]]` versions. A canonical model is
`model_spec.identity.id` plus `version`; `family`, owning GitHub issue URL,
and a full lowercase 40-character git commit SHA complete its immutable
identity. Reusing a model ID/version for a different family, issue, or commit
is a collision. Dataset, feature set, split, evaluation, and experiment have
their own versioned IDs. `experiment.run_id` and
`prediction.inference_run_id` are distinct, deterministic caller-assigned IDs.
No random ID is generated by the validator.

The validated chain is issue + commit → ModelSpec → dataset → feature set and
split → evaluation → experiment/run → Snowflake dataset/experiment/run/job and
registry model/version → Arize project/model/version → prediction/inference
run → monitoring/evaluation evidence state or references. The
`snowflake.registry_model_ref` and `registry_version_ref` and Arize
`model_name`/`model_version` must exactly equal the canonical Atlas model ID
and version. Actual platform handles can be recorded in the other mapping
fields but cannot replace this identity. A Feature Store reference is optional
and only for a later approved use.

The dataset carries a governed source list, immutable snapshot/query reference,
cutoff and as-of semantics, quality and limitation references. The feature
contract points to that dataset and records implementation and point-in-time
availability, leaving detailed feature definitions to #24. The split contract
expresses IID, stratified, temporal, grouped/spatial, or spatiotemporal
metadata, a frozen plan, and protected final holdout. It does not contain row
membership. The evaluation contract binds the plan and holdout to metrics,
baselines, slices, minimum evidence, abstention, and error-cost references.
None of these fields sets universal scientific values.

## Consumption and lifecycle

Validate a complete JSON bundle with `load_bundle(path)` or
`validate_bundle(raw)`. `dump_bundle` validates before serialization. #26 can
use the experiment reference, run ID, resolved input refs, seeds, runtime,
dependencies and code SHA as its run metadata; it must retain failures and
artifact integrity under its own story. #32 can use `prediction` to bind an
inference run and output contract to those inputs. The inference code SHA may
differ from the model training SHA. Neither runner nor output
persistence is implemented here.

Story #39 `atlas-ml-lifecycle/v1` stays unchanged. Pass an existing lifecycle
state as `lifecycle=` when validating a bundle. Any lifecycle references
present must match the canonical model, dataset, feature, split, and experiment
references. Holdout events must identify the same frozen evaluation plan.
The lifecycle validator still owns stage and holdout-access rules; the
contract validator does not infer approval from a populated reference.
The `evidence` component links the inference run to monitoring and evaluation
evidence. `not_collected` forbids a reference; `available` requires one. This
records presence only and makes no judgment about sufficiency or release.

## Evolution and safety

Every component and the bundle have an explicit `/v1` schema tag. Unknown
versions and fields fail. A breaking shape or semantic change requires a new
schema version and explicit migration; do not silently reinterpret v1.
Configuration contains references and metadata, never rows, credentials,
local connection selectors, or API tokens. Validation rejects known
secret-bearing key names at any depth while allowing ordinary explanatory
prose. Only approved adapters may resolve external references or perform I/O.

`config/examples/synthetic-lineage-v1.json` is a complete, deterministic
synthetic example for offline validation. Its placeholder SHA and platform
references are not evidence of a real Atlas model or deployed object. No
Snowflake or Arize connection is needed to validate it.
