# Atlas monitoring policy v1 (Story #43)

The offline Atlas-owned contract lives in `lyme_gap_atlas_ml.monitoring`. It validates against the **complete** Story #41 lineage bundle. The exact canonical model/version, Arize project mapping, and monitoring policy reference must match. Arize IDs are optional external references on monitors and evidence; Arize executes and displays approved signals, while Atlas owns their meaning. Neither the policy nor its examples authorize telemetry or credentials. ADR 0002 already establishes this boundary; Story #43 adds no new architecture decision.

## Regimes and evidence

`pre_label` entries explicitly enable or disable feature drift, prediction drift, missingness, schema quality, outlier/range, freshness/coverage, inference health, and uncertainty distributions. They diagnose inputs, outputs, and operations. They cannot claim demonstrated predictive degradation. `post_label` entries cover performance, calibration/coverage, errors, slices, and baseline comparison only after eligible labels mature. Their metrics and frozen baseline come from Story #30's canonical evaluation contract; this policy creates no competing metrics or holdout use. Thresholds are either `unresolved` or a value with an approval reference. There are no Atlas-wide defaults.

Evidence states are `available`, `unknown`, `insufficient_evidence`, and `not_applicable`. Missing/immature labels and unavailable baselines or telemetry are `unknown`; small samples and incomplete slices are `insufficient_evidence`. A state other than `available` has no metric value. Evidence records retain the reason, windows, reference, slice, metric, threshold reference, sample/label coverage, freshness, source revision/reporting era, timestamp, Arize reference, evaluation reference, and prior event link. Source revision, reporting-era change, outage, missing data, expected quiet period, input/prediction shift, telemetry failure, insufficient labels, and demonstrated degradation remain distinct reasons. An alert starts an investigation, never a model verdict.

Slices are explicit, descriptive-only, reviewed definitions with rationale and separate minimum sample and label coverage requirements. Candidate dimensions include state/region, urban/rural, incidence band, surveillance quality, tick/vector availability, climate/ecological region, population band, and confidence/uncertainty band. A model enables only reviewed slices. Sparse or incomplete slices yield unknown/insufficient evidence, with no causal inference.

## Delayed labels and revisions

Prediction eligibility is supplied by the approved target/horizon and label source contract from Story #23 and the ModelSpec `label_maturity` and `label_revision` references from Story #41; no duration is assumed here. The caller determines whether a linked prediction ID has a mature actual for the evaluation window. Missing and immature labels stay `unknown`. Story #42 sends an actual separately by stable prediction ID. Late or revised labels trigger review or a new evaluation event as configured, using the same frozen #30 plan where applicable. Actual updates and reevaluations append evidence; they never overwrite prior events. Arize join acceptance alone does not prove evaluation sufficiency. Source revisions and reporting-era changes must be recorded as context before interpreting a distribution shift.

## Story #34 consumption and governance

Story #34 consumes pre-label input quality, feature and prediction distribution, inference health, and coverage evidence; post-label performance only after maturity; explicit unknown states; and revision/reporting context. This contract does not schedule inference from #33. An unavailable Story #42 transport produces `telemetry_failure` evidence; recovery is a new linked event. Canonical predictions are never changed by monitoring. Investigation can create a human retraining review referencing evidence, affected windows/slices, label sufficiency, a proposed new #26 experiment, a required #30 plan, expected refresh, resource cost, and reviewer decision. The path is monitor/evaluate → evidence → investigation → human review → new #26 run → #30 evaluation → separate promotion decision. Neither drift nor a review directly retrains or promotes. A confirmed failure becomes a versioned regression case only with reviewer approval, an expected behavior, and target case set reference.

`config/examples/monitoring/` contains wholly synthetic, unapproved pre-label and mature-label policy examples. The two slices demonstrate explicit evidence minima; `evaluate_label` demonstrates sparse and delayed-label outcomes. These are configuration examples, not approved Atlas model thresholds or real monitoring events.
